Continue the Pearl pose-overlay latency investigation using the existing audit and diagnostics.

Read first:

docs/audits/PEARL_POSE_OVERLAY_LATENCY_AUDIT.md

The previous pass added useful instrumentation, but it did not collect physical-device measurements and therefore did not identify the root cause. This pass must turn the instrumentation into an evidence-backed decision.

## Objective

On a physical Android device, determine whether Pearl’s visible pose lag originates primarily from:

1. camera/preprocessing/MediaPipe,
2. native-to-JS event delivery,
3. JS pose/session processing,
4. renderer scheduling and stale-frame handling,
5. React Native SVG commit/drawing cost,
6. or a combination.

Do not perform a large renderer migration yet. Collect controlled evidence first, while fixing only obvious stale-frame or queueing correctness bugs.

## Important current hypotheses

The audit identified these leading possibilities:

### Hypothesis A: Dense React Native SVG rendering

The default renderer is `point_cloud_body`, commonly configured with approximately:

- high density
- up to 900 dots
- large dot scale
- SVG path-based drawing

Synthetic desktop geometry generation was cheap, but React Native SVG path parsing, React commit, native drawing, RenderThread work, and GPU/compositor cost were not measured.

### Hypothesis B: Android native preprocessing

Android currently appears to perform:

- `imageProxy.toBitmap()`
- an additional `Bitmap.createBitmap(...)` rotation copy when required
- MediaPipe inference from the resulting bitmap

This could make even the raw skeleton stale.

### Hypothesis C: Renderer latest-frame handling

Audit the point-cloud RAF backpressure behaviour carefully.

The report indicates that when a render RAF is already pending, later pose updates may return early.

Determine whether the renderer:

- stores the newest incoming pose before returning, or
- completely discards it and later commits geometry derived from an older pose.

The required architecture is:

- every incoming pose replaces `latestPoseRef`
- at most one render callback is scheduled
- the callback reads the newest pose available immediately before geometry generation
- no sequence of old visual frames is queued
- a newer frame must never be replaced by an older frame
- if a pose arrives during a render/commit cycle, the next render should consume the latest pose
- frame dropping is acceptable; stale-frame rendering is not

If the existing implementation violates these invariants, fix it narrowly and test it.

## Stage 1: Verify the diagnostics implementation

Before measuring, inspect the instrumentation added in the previous pass.

Confirm:

- diagnostics are disabled by default
- enabling diagnostics does not emit per-frame console logs
- frame IDs are monotonically increasing
- original source timestamps survive through native and JS
- native durations use one monotonic native clock
- stale and out-of-order events are detected
- metrics are aggregated rather than logged per frame
- instrumentation does not itself create significant allocation or rendering pressure
- renderer update metrics distinguish an update request from an actual visible draw

Document any limitations.

### Pose-age calibration warning

The existing report says JavaScript/native clock alignment is calibrated from an observed event offset.

Do not treat the resulting absolute pose age as scientifically exact if the calibration includes unknown transport delay.

Where possible, compute these values natively before emitting the event:

- source frame age at MediaPipe submission
- source frame age at inference completion
- source frame age at native event emission

Because those timestamps are within the native clock domain, they should be more reliable than deriving all absolute age in JavaScript.

For native-to-JS delivery, report:

- JS receipt minus native dispatch using calibrated clocks
- calibration method
- known uncertainty

Use the metrics confidently for relative A/B comparisons, queue-growth detection, and large delays, but label approximations honestly.

## Stage 5: Instrument renderer scheduling precisely

For each incoming pose result, track:

- source frame ID
- source timestamp
- renderer update request time
- whether it replaced a previous pending pose
- whether it was dropped
- frame ID selected by the scheduled RAF
- geometry generation start/end
- React state publication time
- closest defensible commit/draw indication

Audit both:

- `point_cloud_body`
- constellation renderer

Look specifically for this anti-pattern:

```ts
if (rafPending) {
  return;
}
```

when it occurs before storing the newest pose.

Prefer semantics equivalent to:

```ts
latestPoseRef.current = incomingPose;

if (!rafPendingRef.current) {
  rafPendingRef.current = true;

  requestAnimationFrame(() => {
    rafPendingRef.current = false;
    const newestPose = latestPoseRef.current;
    renderNewestPose(newestPose);
  });
}
```

The exact implementation must fit Pearl’s architecture and avoid per-frame React state where possible.

Also determine whether React state publication itself creates another queue or obsolete commit.

Add tests proving:

- newer frame IDs replace older pending frame IDs
- old results cannot overwrite newer results
- at most one RAF is pending
- a burst of pose events results in rendering the newest pose, not the first pose in the burst
- renderer work does not grow without bound
- unmount cancels pending callbacks safely

## Stage 7: Diagnose using this decision logic

### Result A: Raw skeleton is stale

Prioritise:

1. Android bitmap conversion/rotation
2. MediaPipe inference time
3. delegate activation
4. native main-thread event dispatch
5. stale-event rejection
6. accepted-frame rate and latest-frame semantics

Do not blame the custom figure first.

### Result B: Raw skeleton is fresh but point cloud is stale

The renderer scheduling or React/native rendering path is the dominant cause.

Determine whether:

- stale snapshots are selected before RAF
- React state commits are delayed
- event delivery is blocked by UI-thread work
- too much SVG parsing/drawing prevents timely updates

### Result C: Raw and point-cloud pose ages are similar, but point cloud looks jerky

This is primarily jank and low visual update cadence.

Prioritise:

- RN/SVG draw cost
- RenderThread/UI-thread missed frames
- path complexity
- allocations and garbage collection
- visual batching

### Result D: Raw skeleton is both fresh and smooth, while the full figure is delayed and jerky

Recommend replacing dense React Native SVG rendering with a single batched non-React drawing path.

Do not implement that migration in this pass, but specify the exact recommended architecture.

## Stage 8: Determine the immediate beta safeguard

The current experience is described as extremely laggy and is not acceptable for beta users.

Once the benchmark identifies the lowest-cost configuration that is still visually acceptable, recommend an immediate temporary default.

Prioritise in this order:

1. newest-pose correctness
2. low visible latency
3. stable movement
4. premium visual appearance
5. maximum dot density

A responsive 225–450-dot premium figure is preferable to a delayed 900-dot figure.

Do not automatically switch production defaults unless the measurements clearly support the change. Present the proposed temporary configuration and measured trade-off first.
